# 路由：什么时候该把任务交给 Codex

## 一句话原则

**交给 Codex 是因为它的模型或技能能做成你做不到的事，不是因为它更"高级"。**
每次调用在当前网络下的真实成本是 **2 分钟起**（实测 118–126 秒，即使任务极简）。

## 该交出去

| 任务 | 卡片 | 为什么自己不做 |
|---|---|---|
| 生成位图素材（插画、贴图、封面、mockup、透明底抠图） | `image.generate` | DSH 没有出图工具；Codex 有内置 `image_gen` |
| 一整套风格统一的素材 | `art.assets` | 需要在同一会话里维持风格锚点 |
| 需要深度推理的功能/架构方案 | `design.spec` | 用 Codex 侧的高级模型与 xhigh 推理 |
| 对改动做独立评审 | `code.review` | 换一个模型看，能发现你自己看不见的问题 |
| 用户点名要 Codex | 按目录 | 尊重明确指令 |

## 不该交出去

- 常规编码、文件读写、搜索、跑测试 —— 你自己做又快又准。
- 需要即时交互的探测（跑一条命令看看输出）—— 2 分钟的成本不划算。
- 你已经能确定答案的事 —— 交给 Codex 只是把确定性换成不确定性。
- 需要中途人工介入的任务 —— `codex exec` 是非交互通道，中途无法插话。

## 路由是怎么工作的

1. 你给出 `task`（自然语言）或 `capability`（明确 id）。
2. 给了 `capability` → 直接用；卡不存在则报错并给最接近的候选。
3. 没给 `capability` → 用 `triggers`（权重最高）、`title`、`description` 打分。
4. 最高分与次高分**相等** → 判定为歧义，拒绝执行并要求你明确指定。
5. 完全没有命中 → **拒绝执行**，返回完整目录清单。

### 为什么无匹配时宁可拒绝

猜测路由的失败方式很糟：你会拿到一个「看起来成功、其实答非所问」的结果，而且难以复现。
拒绝一次、让调用方补一张卡或显式指定，长期成本低得多。

## 提高命中率的办法

- **调用方**：任务描述里带上用户原话里的关键词（卡片 `triggers` 就是照这些词写的）。
- **卡片作者**：`description` 写「何时用」，`triggers` 写用户真实会说的短语。
- **不确定时先查**：`codex_capabilities { query: "<任务描述>" }` 会返回排名与**命中理由**，比盲试快。

## 多轮协作

`codex_do` 返回里的 `threadId` 是 Codex 侧会话 id。需要接着上一轮往下做时：

```
codex_do { capability: "design.spec", continueThread: true, task: "把第 3 点展开" }
```

`continueThread: true` 会取该能力**上一次成功运行**的 thread id，用 `codex exec resume` 续接，不必重述上下文。

适用场景：先出方案 → 再评审 → 再修订；或先定风格锚点 → 再逐张出图。

## 长任务

当前网络下每次调用都要经历 5 次重连与 WebSocket 回退。因此：

- 单张出图 ≈ 2–3 分钟；批量素材按张数线性增长。
- 超过两三个任务的批量，建议让用户知道预期耗时，或考虑拆成多次调用。
- `timeoutMs` 别设小；出图类卡片默认 15 分钟，批量 30 分钟。
